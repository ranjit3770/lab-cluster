# 📘 User Guide

## Multi-User Compute Resource & Job Execution Platform

---

# 👑 PART A — SUPER ADMIN USER GUIDE

## 1. Super Admin Responsibilities

As a **Super Admin**, you are responsible for:

* Managing cluster capacity
* Creating and managing users
* Assigning compute quotas
* Monitoring node health
* Handling failures and retries
* Ensuring fair resource usage

You have **full visibility** into the system.

---

## 2. Logging In as Super Admin

1. Open the platform URL
2. Enter your **admin username & password**
3. Click **Login**

After login, you will see the **Admin Dashboard**.

---

## 3. Admin Dashboard Overview

### 3.1 Global Resource Overview

You can view:

* Total cluster CPU
* Total cluster memory
* Used vs free resources

This helps answer:

> “Do we have capacity to onboard a new user?”

---

### 3.2 Node-wise Resource View

For each node, you can see:

* Node ID / name
* Total CPU & memory
* Free CPU & memory
* Health status:

  * UP
  * DEGRADED
  * DOWN
  * MAINTENANCE

⚠️ **Only Super Admins can see nodes**

---

## 4. Creating a User

### Steps

1. Go to **Admin → Users**
2. Click **Create User**
3. Enter:

   * Username
   * Initial password
   * Retry limit
4. Choose **Assignment Mode**:

   * GLOBAL
   * NODE

---

## 5. Assignment Modes Explained

### 5.1 GLOBAL Mode (Resource-wise)

Use when:

* Nodes are similar
* You want flexible scheduling

You assign:

```
CPU: 2
Memory: 2 GB
```

The system:

* Chooses any healthy node
* Enforces limits automatically

---

### 5.2 NODE Mode (Node-wise)

Use when:

* Hardware differs
* Specific machines are reserved
* Lab environments

Steps:

1. Select one or more nodes
2. Assign CPU & memory **per node**

Example:

```
Node-1 → 1 CPU, 1 GB
Node-2 → 1 CPU, 1 GB
```

✔ User jobs will run **only on these nodes**

---

## 6. Quota Validation Rules (Admin)

The system will **reject assignment** if:

* Node does not have enough free resources
* Total assigned quota exceeds capacity

This prevents over-allocation.

---

## 7. Monitoring Jobs (Admin)

From **Admin → Jobs**, you can:

* View all jobs
* See job status:

  * QUEUED
  * RUNNING
  * COMPLETED
  * FAILED
  * RETRY_WAITING
* Inspect retry attempts

You can diagnose:

* User errors
* Infrastructure failures

---

## 8. Handling Node Failures

When a node:

* Misses heartbeats → marked DEGRADED
* Becomes unreachable → marked DOWN

System behavior:

* New jobs stop scheduling on that node
* Running jobs are retried (infra failure)
* Audit logs are created automatically

No manual action required unless maintenance is needed.

---

## 9. Resource Requests (Admin)

Users may request additional resources.

You can:

* Approve (GLOBAL or NODE)
* Reject

Approved changes:

* Apply only to **future jobs**
* Are logged for audit

---

## 10. Audit Logs (Admin)

From **Admin → Audit Logs**, you can see:

* Who did what
* When it happened
* Why it happened

Examples:

* User submitted job
* Admin changed quota
* Node went DOWN
* Job retried

Audit logs are **read-only** and immutable.

---

## 11. Idle User Handling

If a user is idle for **N days**:

* Their quota is revoked automatically
* Resources are released
* User state becomes `IDLE_REVOKED`

You can reassign quota at any time.

---

# 👤 PART B — NORMAL USER GUIDE

## 12. What a User Can Do

As a **User**, you can:

* Submit jobs
* Track job status
* View your resource health

You **cannot**:

* Choose nodes
* Choose CPU or memory
* See other users
* See cluster details

---

## 13. Logging In as a User

1. Open platform URL
2. Enter your username & password
3. Click **Login**

You will see the **User Dashboard**.

---

## 14. User Dashboard Overview

You can see:

* Your job list
* Job status
* Resource health indicator:

  * Healthy
  * In Use
  * Temporarily Unavailable
  * Revoked

No technical infrastructure details are shown.

---

## 15. Submitting a Job

### Steps

1. Go to **Jobs**
2. Click **Submit Job**
3. Enter:

   * Command (e.g., `python train.py`)
   * Arguments (optional)
4. Click **Submit**

That’s it.

⚠️ You do **not** specify:

* CPU
* Memory
* Node

The system handles everything.

---

## 16. Job Status Meaning

| Status        | Meaning                      |
| ------------- | ---------------------------- |
| QUEUED        | Waiting for resources        |
| RUNNING       | Job is executing             |
| COMPLETED     | Job finished successfully    |
| FAILED        | Job failed (no retry)        |
| RETRY_WAITING | Infra failure, retry pending |

---

## 17. Cancelling a Job

You can cancel a job **only if**:

* Status = QUEUED

Steps:

1. Open job
2. Click **Cancel**

Running jobs **cannot be cancelled**.

---

## 18. Job Failures Explained

### User Failure

Examples:

* Script error
* Invalid arguments
* Program crash

Result:

* Job fails
* No retry

---

### Infrastructure Failure

Examples:

* Node crash
* Network issue

Result:

* Job retried automatically (if retry limit allows)

---

## 19. Resource Health Indicator

You may see:

* **Healthy** → You can run jobs
* **In Use** → Your job is running
* **Temporarily Unavailable** → Waiting for infra recovery
* **Revoked** → Idle too long, contact admin

You never see node-level data.

---

## 20. Requesting More Resources

Steps:

1. Go to **Resource Requests**
2. Request additional CPU & memory
3. Submit request

Admin will review and decide.

---

# 🔒 Important Rules (All Users)

* One running job per user
* Fair FIFO scheduling
* No manual retries
* No infrastructure control
* All actions are logged

---

## 🏁 Final Notes

This platform is designed to be:

* **Safe for shared environments**
* **Fair to all users**
* **Easy for admins to govern**
* **Simple for users to operate**

If something fails:

* Users wait or retry automatically
* Admins have full visibility
* No data or resources are lost
