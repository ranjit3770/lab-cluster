## 🧱 Core Entities & Relationships (Authoritative)

### 1️⃣ **USER**

**Central controlling entity**

```
USER
────
id (PK)
role (USER | SUPER_ADMIN)
assignment_mode (GLOBAL | NODE)
max_cpu
max_memory
retry_limit
resource_state
last_job_at
```

**Relationships**

* 1 → N **JOB**
* 1 → N **RESOURCE_REQUEST**
* 1 → N **AUDIT_LOG**
* 1 → N **USER_NODE_QUOTA** (only if NODE mode)

📌 **Why this is correct**

* Every execution, policy, and quota originates from USER
* Assignment mode drives scheduling behavior (GLOBAL vs NODE)

---

### 2️⃣ **NODE**

**Physical / VM worker representation**

```
NODE
────
id (PK)
node_uid
total_cpu
total_memory
free_cpu
free_memory
health_status
last_heartbeat_at
```

**Relationships**

* 1 → N **JOB**
* 1 → N **USER_NODE_QUOTA**
* 1 → N **AUDIT_LOG**

📌 **Why**

* Nodes must be auditable
* Health is time-based (heartbeat-driven)
* Capacity accounting is node-specific

---

### 3️⃣ **USER_NODE_QUOTA**

**Bridge table (NODE-wise binding)**

```
USER_NODE_QUOTA
──────────────
id (PK)
user_id (FK)
node_id (FK)
assigned_cpu
assigned_memory
```

**Relationships**

* N → 1 **USER**
* N → 1 **NODE**

📌 **Key insight**

> This table exists **only when assignment_mode = NODE**

It enables:

* Multi-node assignment
* Hard binding of execution
* Accurate free/used computation per node

---

### 4️⃣ **JOB**

**Execution unit (Ray-backed)**

```
JOB
───
id (PK)
user_id (FK)
assigned_node_id (FK, nullable)
status
failure_type
retry_count
ray_task_id
command
arguments
timestamps
```

**Relationships**

* N → 1 **USER**
* N → 1 **NODE** (nullable in GLOBAL mode)
* 1 → N **AUDIT_LOG**

📌 **Important rules (enforced by service)**

* Only **one RUNNING job per user**
* NODE mode → assigned_node_id MUST belong to user’s quota
* Retry logic tied to failure_type

---

### 5️⃣ **RESOURCE_REQUEST**

**Future quota change request**

```
RESOURCE_REQUEST
────────────────
id (PK)
user_id (FK)
requested_cpu
requested_memory
status
approved_mode
approved_by (FK → USER)
```

**Relationships**

* N → 1 **USER** (requester)
* N → 1 **USER** (approver – SUPER_ADMIN)

📌 **Why separate from USER**

* Keeps approval workflow auditable
* Applies only to **future jobs**

---

### 6️⃣ **AUDIT_LOG**

**Immutable event ledger**

```
AUDIT_LOG
─────────
id (PK)
actor_type
actor_id
action_type
target_type
target_id
previous_state
new_state
reason
timestamp
```

**Relationships**

* N → 1 **USER** (actor)
* Optional → **JOB / NODE / USER**

📌 **Enterprise guarantee**

* Append-only
* Replayable system history
* Explains *why* something happened

---

### 7️⃣ **SCHEDULER_QUEUE**

**FIFO enforcement**

```
SCHEDULER_QUEUE
───────────────
id (PK)
job_id (FK)
user_id (FK)
priority
enqueued_at
```

**Relationships**

* N → 1 **JOB**
* N → 1 **USER**

📌 **Why separate**

* Prevents race conditions
* Enables strict FIFO
* Allows inspection & debugging

---

### 8️⃣ **SYSTEM_SETTINGS**

**Platform-wide policies**

```
SYSTEM_SETTINGS
───────────────
id (PK)
setting_key
setting_value
```

Examples:

* `IDLE_DAYS`
* `HEARTBEAT_TIMEOUT`
* `MAX_RETRY_WINDOW`

## 🧠 Why This ER Design Is **Correct**

### ✅ Matches SRS exactly

* GLOBAL vs NODE enforced structurally
* Node visibility limited by role
* Retry + idle logic supported

### ✅ Scales cleanly

* Adding nodes does not affect users
* Adding users does not affect nodes
* Multi-node assignment is linear

### ✅ Safe by design

* No table allows user-driven node selection
* No job-level resource override possible
* Enforcement lives in scheduler/services
